# Apex Log Insights 1.2.0

This page explains what users, administrators, and browser-store reviewers will receive in Apex Log Insights 1.2.0. It covers the three browser extensions, the shared parser, the offline viewer, CLI, and MCP server. Use it to review the release, prepare store submissions, or decide whether to upgrade.

## Release outcome

Version 1.2.0 updates the five-view investigation workflow with a Salesforce Cosmos-inspired Night theme, resource and heap charts, execution waterfalls, lifecycle steps, record drill-downs, and Apex database cursor analysis. It warns when incomplete log evidence can affect a conclusion, shows the events recorded before a failure, and strengthens the parser when Salesforce logs contain unknown, malformed, deeply nested, or incomplete events. It also makes raw debug-log positions visually distinct from Apex source-code lines.

Chrome, Edge, and Firefox use the same parser and shared viewer. Their manifests and visible version labels are synchronized at `1.2.0`.

### Publication status

The `1.2.0` browser packages are release candidates, not the versions currently served by every browser store. A public-listing review on 2026-08-23 found Chrome at `1.1.22` and Firefox at `1.1.34`; the Edge listing resolved, but its public version was not available to the checker. Store owners must upload and verify the `1.2.0` packages before describing this version as generally available.

The live Chrome and Firefox descriptions also predate the current storage and terminology contracts. Replace them with the maintained [store listing](../../packages/browser-ext/store/listing.md), [privacy policy](../../packages/browser-ext/store/privacy-policy.md), and matching [release notes](../../packages/browser-ext/store/release-notes.md) during submission.

## Browser-extension changes

### Use the Cosmos-inspired investigation theme

Night is the default theme for log analysis. Night and Day map surfaces, text, accents, borders, feedback states, typography, spacing, radii, and shadows to semantic SLDS 2 styling hooks with local fallbacks. The shared theme is included in the standalone viewer, CLI, and browser extensions.

The theme changes colors without replacing the established five-view layout. Triage retains narrative findings and compact metric cards, while Execution Story, Data & Limits, Diagnostics, and Log Explorer retain their existing panel and table hierarchy.

### Show log quality only when it matters

The parser checks for:

- `EXECUTION_STARTED` and `EXECUTION_FINISHED` boundaries;
- Salesforce maximum-log-size messages;
- skipped log sections;
- parser-detected gaps or truncation signals.

The application does not show a routine success panel when no known problem is detected. Triage shows **Log quality warning** only when the evidence is incomplete or uncertain. “Complete” still means only that the application found no known completeness problem; it does not mean Salesforce recorded events excluded by the selected debug levels.

### Review events before a failure

When the log contains an exception or fatal error, **Failure context** shows the recorded event trail leading to it. Each supported event links to its raw-log evidence. Exception and fatal-error messages now preserve embedded `|` characters instead of losing the remaining message fields.

### Distinguish log lines from source lines

The interface now uses two explicit labels:

- **Log line 42** is row 42 in the raw debug-log file. It is clickable and opens Log Explorer.
- **Apex source line 87** is `[87]` in an Apex class or trigger. It is displayed as non-clickable context.

Log Explorer uses `log:42` for an exact raw-log search. Existing `line:42` links remain accepted. Evidence navigation never uses an Apex source line as a raw-log destination. When identical raw text occurs more than once, the viewer uses the parser-declared log position only after verifying that the text matches.

The getting-started guide explains the distinction without adding redundant help beneath the Log Explorer controls.

Analysis tables use separate **Source line** and **Log line** columns. Each cell shows only its number. Both columns are compact and right-aligned; the clickable log-line evidence link is consistently at the far-right edge, while the source-line number is plain text immediately before it.

The parser also enforces its 100 KB safety limit for multiline event text without overshooting it. If Salesforce emits a larger continuation payload, the report retains the bounded text and records a truncation warning instead of silently consuming additional memory.

### Manage cached logs

The extension popup includes **Clear Cached Logs**. This removes cached log payloads without deleting extension preferences. Captured-log storage is bounded to the five most recently opened logs.

### Reliability changes

- Parser workers stop with a clear timeout instead of waiting indefinitely.
- The offline cache includes every viewer module required by the release.
- The service-worker cache version follows the application version, reducing stale-file behavior after an upgrade.
- Repeated failures are grouped with an occurrence count instead of showing the same evidence trail several times.
- The execution story initially shows at most 200 matching events and directs users to filters or Log Explorer for the complete sequence.
- Governor-limit cards identify the transaction scope, preserve percentages above 100%, and state the amount by which a limit was exceeded.
- Diagnostics presents one issue analysis instead of repeating the same findings in two panels, and all evidence coordinates use the explicit **Log line** label.
- The viewer and all three extension shells expose the same five investigation destinations. A release test fails if a tab is omitted or an extra primary destination is introduced.
- `pnpm test:coverage` produces HTML and JSON coverage reports and enforces the documented regression floor before release review.

## Parser and report changes

### Preserve unknown Salesforce events

If Salesforce introduces an event type before Apex Log Insights registers its field semantics, the parser retains it as an `unsupported` timeline event. The retained event includes its type, timestamp, raw text, raw-log line, and parent context. The report preserves the evidence without claiming to understand the event's meaning.

### Describe incomplete event pairs honestly

Paired operations report one of these states:

- `complete`;
- `missing_end`;
- `orphan_end`;
- `closed_by_exception`;
- `closed_at_truncation`;
- `depth_limit`.

`durationIsPartial` is true when a duration depends on incomplete evidence. The UI and report consumers can therefore distinguish measured begin/end durations from inferred closures.

### Preserve correct evidence coordinates

The parser and report keep two separate fields:

- `lineNumber`: the 1-based raw debug-log row used for evidence navigation;
- `sourceLineNumber`: the bracketed Apex source-code line.

This corrects earlier behavior in which an Apex source line could be interpreted as a raw-log row.

### Bound and group parser diagnostics

Malformed input is grouped as `INVALID_LOG_LINE`, `UNSUPPORTED_EVENT`, or `MALFORMED_EVENT`. Each group records its count, first and last raw-log lines, and up to three bounded samples. The compatibility warning list is capped so an unexpected file cannot create unbounded diagnostic output.

Repeated parser issues retain their occurrence count and first and last occurrence. Report issues also include the supporting event type and enclosing context when the parser can identify them.

### Handle deep nesting without losing the remainder

At 500 nested levels, the parser reports `Maximum-Nesting-Depth`, marks the affected subtree incomplete, and switches to an iterative fallback. It preserves the remaining events without adding more recursive calls or presenting a zero-duration leaf as a normal result.

### Provide asynchronous continuation clues

The report extracts available clues for Queueable, Future, Batch Apex, and event-service activity, including observed identities and `707` asynchronous job IDs. A clue directs the user to analyze the related transaction's separate debug log. It never claims that the child transaction is contained in the current log.

## CLI and MCP changes

The CLI adds `/api/health` for local diagnostics. Its local server binds to loopback, limits supported HTTP methods, protects log routes, and prevents single-file mode from listing sibling logs.

The packaged `apex-log` executable contains one Node shebang and is exercised through its built entry point before release.

The MCP server adds `compare_logs`, which returns candidate-minus-baseline deltas for two local inputs. MCP input handling now:

- requires exactly one of `logText` or `filePath` per input;
- accepts only relative `.log` file paths;
- rejects traversal segments, absolute paths, and null bytes;
- limits each log input to 25 MB;
- makes no Salesforce or third-party network request itself.

MCP results pass to the configured AI client. That client may send them to a cloud model. The optional `redact` setting masks recognized sensitive values but cannot guarantee anonymity.

## Privacy and storage

Normal browser analysis, the offline viewer, and CLI parsing run locally. The product does not add telemetry or an Apex Log Insights upload service.

The browser extension can retain recent captured-log payloads in extension storage so reports can be restored. Use **Clear Cached Logs** to remove them. Comparison inputs are not added to that cache.

For the complete boundary, including browser behavior and MCP downstream transmission, read [Privacy and security](../user-guides/privacy.md).

## Known boundaries

- One Salesforce debug log represents one logged execution context, not an entire asynchronous business process.
- Queueable jobs, future methods, Batch Apex executions, scheduled work, and platform-event subscribers normally create separate logs.
- Completeness checks cannot recover events omitted by Salesforce debug-level configuration.
- A retained unsupported event preserves evidence but does not receive event-specific interpretation until its format is registered.
- PDF generation and export are not part of this release.

## Validation performed

The release candidate passed the repository validation gate:

- formatting and ESLint checks;
- TypeScript checks for core, CLI, MCP, and browser-extension packages;
- automated parser, report, browser-shell parity, and viewer compatibility tests;
- version synchronization across packages, manifests, viewer assets, offline cache, and popup label;
- documentation consistency and local-link checks;
- Chrome, Edge, and Firefox release builds.

The evidence-navigation simulation used conflicting coordinates, log line 3 and Apex source line 87, and confirmed that only `log:3` was generated as a link. The three packaged extensions were inspected for the source-line distinction, concise Log Explorer controls, and version `1.2.0`.
